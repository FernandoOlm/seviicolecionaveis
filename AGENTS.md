Checkout pickup validation lives in browser-safe helpers under src/lib, with focused tests; event pickup uses shippingMethod arrange with schedule_kind 'event', orders.event_id linking the events table, and the event name persisted in order notes, keeping all payment paths compatible.
Pickup events (Retirada em eventos) live in the events table with rules in src/lib/events.ts (1h slots, per-day closing 24h before start, reopen at 10h the day after the event ends); admin CRUD is at /admin/eventos, the client calendar is EventSlotPicker, and reopening runs in the same pickup-reopen cron hook.
Buyer receipt confirmation uses an authenticated server function and a row-locking owner/status-checked database RPC, persisting buyer receipt timestamp/user on orders; this prevents concurrent or forged transitions and leaves payment/stock untouched. Store notices reuse the existing email sender and configured store recipient, falling back to the existing operational mailbox.
Schedule confirmations run in the paid-order pipeline with separate per-order client/store idempotency keys, reuse the existing email sender and app_settings recipient, and generate Google Calendar links in a pure tested helper; no OAuth or email queue is needed.
Regular-order statuses, labels, and paid-stage classification live in the browser-safe order-status module; reuse them across admin, customer, email, payment, and stock flows to prevent lifecycle inconsistencies. Service orders retain a separate lifecycle.- Scheduling availability (24h lead, America/Fortaleza) and pickup reopen rules live in src/lib/scheduling.ts and are enforced both in the picker and server-side; reopened pickups are flagged on the order (history kept, card stack deadlines untouched) by a daily cron right after the 14h deadline.
- Admin shipping/pickup edits go through an admin-checked server function with pure rules in src/lib/admin-shipping-edit.ts, appending orders.shipping_edit_history and reusing the schedule-confirmed email; keeps reopen crons and stack deadlines working unchanged.
- Manual admin orders (origin 'manual') are created by an admin-checked server function in src/lib/manual-order.server.ts with pure totals/stock rules in src/lib/manual-order.ts; paid ones reuse markOrderPaid (stock, points, stack, emails) so they behave like site orders, internal notes live in the admin-only order_admin_notes table, and 'Definir depois' uses shipping_method to_define.
- Fulfillment choice/change/cancel alerts go through one central notifyFulfillmentChange (src/lib/fulfillment-alerts.server.ts, pure rules in src/lib/fulfillment-alerts.ts): it writes admin_notifications with a unique dedupe key and sends client/store 'fulfillment-update' emails independently with retries; every flow (paid checkout via sendScheduleConfirmations, Pilha service orders, admin edit, reschedule, auto reopen) must call it instead of sending its own emails.
- Manual event-hub inclusions (src/lib/event-hub.server.ts, pure rules in src/lib/event-hub.ts) claim orders.event_id atomically, snapshot the prior modality in orders.event_previous for 'Remover do evento', and reuse adminEditOrderShipping (allowAnyMode) so history, emails and the central alert stay in one path.
- Hand delivery (Entrega em mãos) area and fee rules live in src/lib/hand-delivery.ts, checked in UI and server (checkout assertSchedule, service orders, admin edit/manual); fee status changes only via admin-checked setHandDeliveryFeeFn, guarded by a DB trigger so customers can't alter it.
